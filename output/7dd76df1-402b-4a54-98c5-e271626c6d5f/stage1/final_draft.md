# 多智能体软件开发系统 项目说明

## 一、技术方案

### 1.1 总体架构

系统以「角色分工 + 状态图编排」为核心，自下而上分为四层，全项目 1180 行（Python 875 行、前端 305 行）。

- **LLM 抽象层**（`core/llm.py`，307 行）：统一 `BaseLLM` 接口，提供三种实现——`MockLLM` 用规则模板生成确定性输出；`OllamaLLM` 走 Ollama 原生 `/api/chat` 协议，仅依赖 `requests`；`OpenAILLM` 面向 OpenAI 兼容端点，可指向 DeepSeek、通义千问等。工厂函数按 `LLM_PROVIDER` 选择实现，切换实现不触碰任何上层代码。
- **角色定义层**（`agents/definitions.py`，119 行）：以数据类 `AgentRole` 描述五个角色的系统提示词、名称、图标与主题色，形成注册表，新增角色只需追加一条定义。
- **编排层**（`core/graph.py`，193 行）：用 LangGraph `StateGraph` 定义有向状态图。状态 `AgentState` 为 `TypedDict`，携带任务、协作历史、当前角色、最近输出与迭代计数五个字段；节点只返回增量，由框架负责合并。
- **服务层**（`web/server.py` + `static/`，290 行）：Flask 提供 REST 与 SSE 接口，前端为原生 HTML/CSS/JS，不引入前端框架。

### 1.2 协作流程与反馈循环

主线为「产品经理 → 架构师 → 开发者 → 测试工程师 → 代码审查员」。图上另设两条条件边：测试节点之后，判定通过则进入审查、否则回流开发者；审查节点之后，判定通过则结束、否则回流开发者修改。开发者节点每次执行使迭代计数加一，达到上限（默认 2 次）即推送 `loop_capped` 事件并终止，避免小模型反复改不出结果时无限循环；图执行本身另设递归上限作为兜底。

### 1.3 关键实现要点

1. **结论判定不依赖宽泛关键词**。判定函数优先用正则抓取「结论：通过 / 不通过」标记，且先判否定词（「不通过」包含「通过」，必须先判否定）；抓不到标记时才退化为关键词匹配。角色提示词强制要求末行输出固定格式结论，形成「格式约定 + 三级回退」的双保险。
2. **上下文预算控制**。每轮把前序产出拼接后送入模型，超过字符预算（默认 6000）即截断并保留最近产出，避免早期内容占满小模型的 8192 上下文。
3. **参数与模型驻留**。生成温度 0.6、上下文 8192、单次生成上限 768 token、请求超时 300 秒；请求体携带 `keep_alive`，使模型在内存中驻留，避免每次运行重复承担 20~30 秒冷启动。
4. **实时可视化**。节点开始、节点完成、循环终止、运行结束四类事件经内存队列广播给所有订阅者；新连接先收到当前状态快照，断线重连可恢复进度。
5. **并发保护**。已有任务运行时提交新任务返回 409，运行状态全局单例，避免多任务争抢同一份模型资源。

## 二、创新点

1. **反馈闭环而非单向流水线**。测试与审查被设计为可控回路，不通过即回流修复，配合迭代上限形成「可收敛的迭代」，比一次性生成更贴近真实开发过程。
2. **把「判定」当成工程问题处理**。结论格式约定、否定优先、三级回退三层设计，使 3B 级小模型也能稳定驱动流程分支——实测无需任何提示词修补即可正确终止，这是小模型跑多智能体最容易翻车的一环。
3. **一套代码两种演示形态**。模拟模型与真实模型通过一个环境变量切换：需要零依赖、无网络、无密钥的快速演示时用模拟模型，需要真实推理时切本地 Ollama 或在线兼容端点，前端与编排层完全不变。
4. **面向弱算力的工程约束**。上下文预算、生成上限、迭代上限、模型驻留四项约束共同作用，使「普通笔记本 CPU + 3B 模型」这类低成本环境也能跑通完整多智能体闭环。
5. **过程可见即可评审**。事件流逐节点推送，角色卡片、颜色、图标与协作历史同源，评审者能直接看到任务在角色之间如何流转，而不只是看到一个最终答案。

## 三、验证结果

| 验证项 | 方法与条件 | 结果 |
|---|---|---|
| 图执行顺序 | 直接调用编排类运行任务 | 产品经理→架构师→开发者→测试→审查，历史 5 条 |
| 结论路由 | 审查输出含「结论：通过」 | 正常进入结束节点，无回流 |
| 迭代保护 | 迭代上限设为 2 | 未通过时回流计次，达上限推送终止事件 |
| Web 全链路 | 提交任务并轮询状态接口 | 任务启动、进度递增、结束时间正常写入 |
| 实时推送 | 订阅事件流 | 首帧返回状态快照，随后逐节点推送 |
| 接口健壮性 | 调用角色/状态/运行/首页接口 | 均正常响应；重复提交返回 409 |
| 真实模型 | 本地 Ollama + qwen2.5:3b（Q4_K_M） | 五个角色均产出有效内容，单任务 340~390 秒，生成速率约 7 token/秒 |
| 模拟模型 | 切换为模拟实现 | 同一链路 2 秒内完成，用于流程回归 |

以「写一个判断回文字符串的 Python 函数」为测试任务，真实模型下开发者给出了完整函数实现，测试给出单元测试用例与固定格式结论，审查给出结构化优缺点分析与「结论：通过」，流程按预期收敛。

## 四、当前局限

1. **生成不等于落地**。开发者输出的代码块只进入协作历史与界面，不写入磁盘、不被执行；测试报告由模型自述而非真实运行结果。这是「演示级」与「工程级」的分界线，也是当前最大的短板。
2. **小模型能力与速度上限**。3B 模型在 CPU 上约 7 token/秒，单任务接近 6 分钟；架构设计段落出现明显循环赘述，审查意见偏笼统，任务规模一大就吃力。
3. **判定仍依赖文本**。结论判定本质是格式约定加正则匹配，模型不按格式输出时只能退化猜测，鲁棒性有限。
4. **单任务串行、无持久化**。同一时刻只能运行一个任务；协作历史仅存于内存，服务重启即丢失。
5. **前端只做展示**。缺少代码文件预览、测试报告下载、历史回放等交互能力。

## 五、后续计划

1. **让代码真正落地**。开发者输出写入工作目录，测试在受限子进程中实际执行，审查基于真实改动与覆盖率数据，把「自述质量」换成「实测质量」。
2. **用结构化输出替代文本约定**。约束各节点输出结构化结论对象（状态、理由、待修项），彻底移除正则判定。
3. **任务队列与持久化**。引入任务队列与轻量数据库，记录任务、历史与产物，支持中断恢复与历史回放。
4. **按角色分级选模型**。架构与审查用能力更强的模型，实现与测试用小模型，配合流式输出降低首字等待，在质量与时延之间取得平衡。
5. **角色与流程可扩展**。开放角色注册表与流程图配置，支持「安全审查员」「性能优化师」等自定义角色。
